# 機能分担戦略

## 目的と現在の状態

4人で並行して開発し，「PCで作業・途中報酬獲得 → 一時停止してiPhoneで小休憩 → 再開 → 終了時に全未使用報酬を破棄・制限解除」という流れを成立させる．[プロダクト戦略](1.プロダクト戦略.md)と[機能・非機能要件](2.機能-非機能要件.md)に基づく分担案とする．

現在は検討途中．1人がiOS側のPoCを行う予定であり，残り3人の担当者名・日程は未確定．以下のA〜Dは役割を示す仮称で，実装の完了状況を示すものではない．

## 4人の分担案

| 担当 | 主な責任 | 対象要件 | 最初の成果物 |
| --- | --- | --- | --- |
| A：iOS・PoC | 許可取得，対象アプリ選択，制限・一時解除・再制限．PoC後は認証・残高表示・API連携を担当 | I-01〜I-09，I-11 | 仮の報酬時間で「制限 → 解除 → 再制限」を実機確認できる |
| B：デスクトップの計測・判定 | 最前面アプリ・入力・アイドルの計測，アプリ分類，集中度と作業・脱線・保留の判定 | M-04〜M-06，M-09，M-11〜M-13 | 計測結果と判定根拠をCが扱える形式で返せる |
| C：デスクトップの画面・連携 | タスク設定，タイマー，結果表示，認証画面，作業記録送信，確定した報酬の表示 | M-01〜M-03，M-07〜M-08，M-10，M-14 | 仮の計測データで「開始 → 定期送信 → 一時停止・再開 → 終了・結果表示」を操作できる |
| D：バックエンド・インフラ | API契約，認証・認可，作業記録，報酬獲得・消費，DB，デプロイ | B-01〜B-06 | テスト用の作業記録から報酬付与・残高取得・消費ができる |

要件の優先度は機能・非機能要件に従う．担当範囲に含まれていても，推奨・発展機能を最初からすべて実装することは求めない．

### 追加要件の担当案（導入優先度は未定）

| 担当 | 追加する責任 | 対象要件 |
| --- | --- | --- |
| A | 2つの制限モード，標準アプリの常時許可とSafariの扱い，実利用時間の計測，再開時の再制限，iPhone通知表示とグループ画面 | I-12，B-07，B-08，G-01，G-02 |
| B | 最小時間判定に使う一時停止を除いた計測時間，終了・中止時の記録 | M-15 |
| C | 最小時間設定，本人による終了・中止，起動時ポップアップ，作業状態同期，PCのグループ画面・通知 | M-15，M-16，B-07，B-08，G-01，G-02 |
| D | 開始・再開と利用許可失効の整合性，通知抑制，グループ・招待・所属管理，PCとiPhoneへの通知配信 | B-07，B-08，G-01，G-02 |

A・C・Dで通信断中の再制限と通知抑制の限界を確認し，C・DでPC通知の配信方式を決める．グループの招待方式・管理権限・共有情報は全員で確定する．

### 責任の境界

デスクトップアプリはWails v2（Go + Web UI）を用いてmacOS・Windowsに対応する．BはGoの共通計測インターフェースとOS別実装・権限のPoC，CはWeb UI・Wailsとの接続・端末内GoからのConnect RPC通信を担当する．B・Cが両OSで結合確認する．

- **BとC**：Bは計測・判定処理，Cは画面とセッション操作・API連携を担当する．アプリ分類の判定ロジックはB，設定画面はCが担当する．同じ `desktop/` 配下でも担当モジュールを分け，共通の型の変更は両者で確認する．
- **BとD**：Bが作業状態・集中度の判定材料と結果を提供し，Dが合意した換算ルールに基づいて報酬を最終確定する．残高の正本はサーバー側とし，Cは確定結果を表示する．
- **AとD**：Dは報酬の消費・残高管理，AはiPhoneでの制限・解除・再制限を担当する．消費成功後に解除できなかった場合の扱いは共同で定義する．

API定義・DB変更・インフラ設定の編集主担当はDとする．APIを利用するA・Cと，計測データを提供するBが関連する変更をレビューする．

## 並行開発の進め方

| 段階 | 進め方 | 完了の目安 |
| --- | --- | --- |
| 1．成立条件の検証 | AはiOSの制限・解除，Bはデスクトップの計測をPoCで確認する．Cは仮データで画面，Dはテスト用リクエストでAPI・DBを構築する | 各担当の最初の成果物が動き，実現できること・制約・未確認事項を共有できる |
| 2．最小の全体接続 | Bの計測結果をCからDへ送り，確定した報酬をAで取得・消費する | 作業中の報酬獲得，小休憩，再制限，終了時の残高破棄と解除まで確認できる |
| 3．品質の確認 | 通信切断・再送・権限拒否・残高不足・再起動を担当間で確認する | 機能・非機能要件の受け入れシナリオを確認し，未達事項を記録できる |

A・BのPoCで制約が判明した場合は，影響する要件と構成を4人で見直してから接続を進める．PoCの手順・実機条件・検証結果は[PoC戦略](3.poc戦略.md)に整理する．同資料には追加要件の検証項目を記載し，実機検証結果は未記入．

## 着手時に合わせるインターフェース

| 接続・境界 | 合意する内容 | 主担当・確認者 |
| --- | --- | --- |
| 計測 → 画面 | セッションID，作業・脱線・保留の時間，判定根拠，計測不能時の状態，開始・一時停止・終了の通知 | B・C |
| デスクトップ → API | 作業記録の送信形式，送信タイミング，再送の識別，報酬の確定結果 | D・C，計測項目はBも確認 |
| API → iOS | 残高，消費時間，消費結果，解除失敗時の扱い | D・A |
| 全体共通 | 時間の単位，認証方式，報酬換算ルール，実利用時間の計測・同期方法，作業再開時の失効順序 | 全員 |

API契約は[API仕様書](../spec/3.API仕様書.md)，作業・時間・残高の意味は[ドメインモデル定義](../spec/4.ドメインモデル定義.md)に記載する．仮データも合意した形式に合わせ，接続時に置き換えられるようにする．本書では具体的なフィールド定義や通信仕様を固定しない．

## 品質確認と負荷の分担

| 観点 | 主担当・協力者 |
| --- | --- |
| 二重付与・二重消費・認可・秘密情報・運用（N-01，N-04，N-06，N-10） | Dが主担当．A・Cがクライアントからの再送・認証・通信を確認 |
| 通信障害と復旧（N-02） | A・Cが表示と再試行，Dが処理結果の整合性を担当 |
| 解除時間の整合性（N-03） | Aが実機確認，Dが消費結果との整合を確認 |
| プライバシー・性能・操作性・互換性（N-05，N-07〜N-09） | Bが計測，Cがデスクトップ画面，AがiOS，DがAPI・保存・ログの範囲を担当 |

Dに負荷が集中しやすいため，まずAPI・DB・最小限のデプロイを優先する．推奨のAPNs通知や利用履歴，発展の進捗検出・スクショ解析は基本ループの接続後に扱う．結合確認はCが取りまとめ，障害は該当する担当が修正する案とする．

## 今後決めること

- 各担当者の名前，得意分野，作業可能時間と日程．AのPoC後のiOS実装継続も含めて確定する．
- macOS・Windowsの対応バージョン・CPUアーキテクチャと計測可能な情報，Web UIのフレームワーク，iOSの実機検証・配布に必要な環境．
- インターフェース，報酬換算，実利用時間の計測精度と，通信・解除失敗時の扱い．
- PoCの結果を踏まえた初期版の範囲，担当間の支援，結合確認の日程．
