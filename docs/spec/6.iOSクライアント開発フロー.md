# iOSクライアント開発フロー

## 1. 目的と現在地

バックエンドAPIが利用可能になった後、iOS担当がUIモックからAPI接続、端末制限までをどの順で実装・確認するかを定める。APIの業務上の意味は[API仕様書](3.API仕様書.md)、作業・報酬・利用枠の不変条件は[ドメインモデル定義](4.ドメインモデル定義.md)を正とする。本書はAPI契約や未決の業務ルールを新たに確定するものではない。

現在の状態：

- `mobile/` にSwiftUIアプリがある。初回未認証時はメールOTPの歓迎・ログイン画面を表示し、保存済みsessionとbackend業務Userの同期が成功すればタブ画面を開く。ログインを後回しにしても端末内設定は使え、ホーム・グループ・履歴ではログイン導線を表示する。設定タブからもログイン状態の確認・変更ができる。Debugでは開発者向け接続先入力欄を表示し、ReleaseではInfo.plistのBuild Settings値を使う共通設定を実装した。OTP後のAuth session取得は実機で行われたが、EnsureUser／GetMeのstaging成功は未確認。現行Xcode projectにはRelease用接続値を注入する`.xcconfig`／CI設定がなく、利用者へ値を入力させず配布するための設定作業が残る。Desktopも同じSupabase project・メールOTPアカウント・backend環境なら同じ業務Userへ対応する設計で、アカウント連携用ペアリングコードはない。新規／既存アカウントの両端末E2Eは未確認。FamilyControlsの本人認可・対象選択、ManagedSettingsによるShield、iPhone端末登録、制限ポリシー同期に加え、セッション状態との照合、適用状態報告、ReserveUsageGrant／GetUsageGrant／ReportUsage、DeviceActivity monitor extensionを実装した。extensionの実機向けDebug／Releaseビルドと署名、アプリの実機インストール・起動・ホーム画面表示は確認済み。App Groups共有、実機監視イベント・期限後Shieldも未確認。
- OTPメールの到達は確認したが、新規登録時のメールは標準のConfirm signupリンクで、本文に`{{ .Token }}`も文字列のまま含まれていた。リンク先は`localhost`であり、アプリ内OTP認証の成功を示していない。Confirm signupとMagic link or OTPのテンプレートを開発用Supabaseプロジェクトで確認する。
- backendにはidentity／focus／reward／restrictionのproto、Go／Connect生成物、RPC handlerと認証interceptorの実装コードがある。したがって「業務APIのコードがない」状態ではない。
- API仕様書では業務RPCを契約案として扱っており、iOSが依存する契約としての確定・互換性方針は未確認。mobileは`URLSession + Codable`のConnect JSON transport、Debug用health確認画面、`GetCurrentSession`／`GetBalance`／`GetRestrictionState`を呼ぶ`APIHomeRepository`を実装した。Supabase URL・公開用key・API URLをDebug設定し、認証セッションがある場合にホームでAPI応答を使う。Swift DTOのproto JSON互換性、版整合性、環境別接続設定とstaging検証は未完了。
- ローカルComposeはGo APIを再ビルドして起動済み。`/healthz`は200、`GroupService.ListGroups`と`CreateGroup`および招待・退出の3ルートは未認証時に401を返し、認証ガード付きで登録されていることを確認した。migration `00006_group_operations.sql`と`00007_group_invitations.sql`はローカルDBへ適用済み。認証済みの作成・招待・参加・退出操作、外部環境へのdeploy・DB migration、staging接続は未確認。
- UIモックの画面対応と未接続範囲は[mobile README](../../mobile/README.md)を参照する。

### ログイン導線と接続設定

初回起動時にログイン状態を復元し、未認証なら歓迎画面でメールOTPを案内する。保存済みsessionがある場合は`EnsureUser`／`GetMe`でbackendの業務Userも確認してからタブ画面へ進む。Auth sessionはあるがbackend同期が失敗した場合はログイン済みAPI画面へ進まず、エラー・再試行・端末内利用・別アカウントでのログインを表示する。ログインを後回しにした場合は端末内設定を利用でき、認証が必要なホーム・グループ・履歴にはログインボタンを表示する。Debugは開発者が接続先を編集できる。Releaseはビルド時に組み込むSupabase／Connect設定を使う設計であり、利用者がURL・公開キーを入力する必要はない。ただし現行projectには値を注入するRelease`.xcconfig`／CI設定がないため、配布前に環境別の公開値を設定する。

次の順で認証の縦切りを完了する。

1. 開発用Supabaseプロジェクトの`Confirm signup`と`Magic link or OTP`テンプレートを確認し、OTP本文に実際のコードを埋め込む。Sourceへ設定した本文で`{{ .Token }}`が文字のまま残らないことを確認する。本番プロジェクトの認証設定は変更しない。
2. 最新のDebugビルドをSimulatorへインストールし直し、未認証なら歓迎・ログイン画面、認証済みならタブ画面が表示されることを確認する。
3. 開発用Project URLとPublishable key、Connect API URLを入力し、メールの数字コードをアプリ内で検証する。メール内のlocalhostリンクは開かない。
4. Supabase Auth sessionが取得でき、そのaccess tokenで`EnsureUser`と`GetMe`が成功することを確認する。Auth session取得は実機で行われたが、業務User登録・取得はAPI応答エラーがあり、引き続き確認が必要。
5. 上記が成功した後に段階1の認証確認を完了とし、API契約・staging接続準備が揃ってから段階2の読み取り専用ホームへ進む。

## 2. 開発の原則

1. **ホームの読み取りから始める**。認証と読み取りAPIが揃えば、OS制限のPoCを待たずにホーム画面を実APIへ接続できる。
2. **サーバーを報酬残高の正本とする**。iPhone内で残高を減らしたり、API応答を受けずに成功表示したりしない。
3. **通信型と画面表示型を分ける**。protobuf／ConnectのDTOをそのままSwiftUIに渡さず、Data層でドメイン表示モデルへ変換する。
4. **仮データ経路を残す**。`MockHomeRepository` は画面PreviewとDebug確認用に保ち、API接続後も契約・エラー状態を再現できるようにする。
5. **OS制限はAPI接続と別の完了条件にする**。サーバーの制限要求、API受理、iPhoneで実際に適用できた状態を別々に表示する。
6. **未決の仕様をUIで確定しない**。選択肢、制限モード、利用時間の範囲、失敗時の返還などは決定記録ができるまで読み取り専用または案内表示にする。

依存関係は次の向きに保つ。

```text
SwiftUI View
    ↓
ViewModel / Use Case
    ↓
Repository protocol
    ├── Mock Repository（Preview・Debug）
    └── API Repository（契約確定後）
          ↓
      生成済みConnectクライアント／通信adapter

RestrictionController protocol
    └── OS制限実装（PoC・権限・配布条件の確認後）
```

## 3. バックエンドから受け取る「接続準備完了」の成果物

「APIができた」という口頭共有だけで接続を始めない。次の成果物を確認する。API所有者はバックエンド担当、iOSの使い勝手・エラー状態はmobile担当がレビューする。

| 成果物 | 確認内容 | 接続開始条件 |
| --- | --- | --- |
| 確定したproto／API契約 | package・サービス・メソッド、フィールド番号、秒／UTC等の単位、optional・enum、ページング、版管理 | iOSが呼ぶメソッドの破壊的変更がなく、API仕様書に反映済み |
| iOS DTO・クライアント | Swift生成型を使うか、proto JSONに対応したCodable DTOを保守するか。生成／更新手順、所有者、互換性確認方法 | 今回は`URLSession + Codable`を選択。DTOがproto JSONのfield name・enum・int64・timestampを正しく扱い、backendとの更新責任が決まっている |
| Connect通信方式 | iOS向けtransport、base URL、TLS、タイムアウト、HTTP／Connectエラーの変換 | 標準`URLSession`でConnect JSONを扱う方針を選択済み。環境別URLとエラー表示・再試行の契約が揃っている |
| 認証仕様 | ログイン、access token取得・更新・失効、logout、アカウント状態、401/403時の挙動 | バックエンド認証担当とmobile担当でtoken lifecycleを確認済み。秘密情報はKeychain等の安全な保管方法を定義 |
| 環境 | local／development／staging／productionのURL、TLS証明書、テストアカウント、環境切替方法 | URL・秘密情報をソースへ固定せず、stagingでiPhoneクライアントから疎通可能 |
| 認証済みユーザー・端末 | `GetMe`、`RegisterDevice`、端末IDの生成・保持・再インストール・失効の契約 | iPhoneの登録時期、二重登録、1台制限、交換・失効時の挙動が定義済み |
| 業務APIの実行可能環境 | DB migration適用、API起動、health確認、seed／テストデータ投入、ログの相関ID | stagingで本人ごとのデータを使い、成功・失敗応答を再現できる |
| エラー・再試行 | Connect codeとdomain errorの対応、operation ID、結果照会、retryable判定 | `docs/spec/3.API仕様書.md` のエラー分類とクライアント表示・再送動作が対応済み |

上記のうち認証、proto／Swift生成、Connect transport、対象API、staging URLのいずれかが未確定なら、実ユーザーのAPI接続は開始せず、仮データで画面作業を続ける。

### 現在の準備状況

現行backendソースには`EnsureUser`、`GetMe`、`UpdateDisplayName`、`UpdateAvatar`、`RegisterDevice`等のRPC handlerがある。mobileはメールOTP認証時にプロフィールアイコンを選び、本人の`avatar_id`を保存できる。プロフィール画像はAsset Catalogに同梱し、Group APIからIDを受け取ってグループメンバーへ表示する。新規migrationは既存Userへ既定値`chick`を設定する。これはstaging・実機でのAPI動作確認を意味しない。開発用Supabase Project URL／publishable key、OTPテンプレート・SMTP、API URL、backendのJWT issuerを同一環境で揃える。Debug画面の`GET /healthz`はプロセス生存のみを確認し、未認証のため業務RPC疎通とは別である。

`MockHomeRepository`はSwiftUI Preview専用とし、アプリ画面からサンプル状態へ切り替えるDebug UIは削除した。`APIHomeRepository`は現行proto案に基づく読み取り実装で、通常起動時はAPIを利用し、未設定・通信失敗時はエラーを表示する。3つの応答は別々に取得するためsession IDが食い違う場合は表示を失敗扱いにするが、共通snapshot/versionによる原子的整合性は提供しない。API契約の確定、DTO互換性と同時更新のstaging検証は引き続き必要。

## 7. モバイル側の段階完了チェック

各段階のPRには、次を記載する。

- 対象画面・API・仕様見出しと、今回の範囲外。
- Mock／APIのどちらで確認したか。staging利用時は環境名のみ（token・個人情報は記録しない）。
- 起動、再起動、通信断、401/403、競合、重複要求など対象となる確認と結果。
- サーバー確定値、端末内の希望状態、iOS適用確認、未同期情報が混同されないこと。
- 未決事項の変更が必要なら、実装で仮定せず、API仕様書またはドメインモデル定義の更新を先に行ったこと。
