# デスクトップ共同開発

## 1. 目的と適用範囲

Mac担当者が共通基盤を先に作り，その基盤を使ってMac担当者とWindows担当者が各OSのUIを並行開発する．Wails v2のアプリを`desktop/`に1つだけ置き，Goモジュール・フロントエンドの依存・画面向け契約を共有する．OSごとにアプリ一式を複製しない．

本書は今後の実装に適用する開発方針であり，共通基盤・各OSのUIが実装済みという意味ではない．技術構成は[フロントエンド構成](6.フロントエンド構成.md)，業務規則は[ドメインモデル定義](4.ドメインモデル定義.md)，クラウド通信は[API仕様書](3.API仕様書.md)を正本とする．本書はクラウドのRPC・報酬計算式を確定しない．

## 2. 共通化とOS別実装の境界

画面内容・操作・状態の意味を共通化し，OSの操作習慣やネイティブ機能に関係する部分を分ける．共通化のためにMacの見た目をWindowsへ強制せず，OS別の見た目のために業務処理を二重実装しない．

| 対象 | 共通部分 | Mac／Windowsそれぞれの担当部分 |
| --- | --- | --- |
| アプリ基盤 | Wails v2，React・TypeScript・Vite，依存とビルド設定 | OS別のウィンドウ設定，アイコン，配布設定 |
| 画面内容 | タスク入力，時間・残高・結果・同期状態の表示部品 | 画面の外枠，ナビゲーション，配置，必要な表示差分 |
| スタイル | 色・余白・時間表記などの共通定義，部品の意味 | フォント，タイトルバーとの余白，OS固有の寸法・スタイル |
| 画面状態 | 表示用の型，状態保持，読み込み・失敗・再試行，操作中の重複抑止 | OS対応状況に応じた案内の表示 |
| Goとの接続 | bridge，Wailsイベントの購読・解除，入出力の変換 | 共通bridgeが公開するOS機能の呼び出し先 |
| 端末内処理 | セッション状態，保存・同期・API連携，計測の共通インターフェース | 計測・権限取得，トレイ，メニュー，ショートカット，安全な認証情報保存 |
| 開発・確認 | デモシナリオ，契約テスト，表示の受け入れ条件 | 各OSのWebViewでの表示・操作・ビルド・実機確認 |

UI担当の分担は[機能分担戦略](../strategy/4.機能分担戦略.md)のCをOS別に分けるものとする．計測・判定を担当するBの責任を，各OSのUI担当へ自動的に移さない．OS固有の計測処理はBと接続契約を確認して導入する．

## 3. 配置と依存方向

以下は配置方針である．実装のあるディレクトリだけを作り，空のパッケージは先行作成しない．

```text
desktop/
  main.go                         # 共通の依存組み立てと起動
  platform_darwin.go               # Macの起動設定（GoのOS別ファイル）
  platform_windows.go              # Windowsの起動設定
  go.mod / go.sum / wails.json     # 共通基盤担当が管理
  internal/
    app/                          # 共通の画面向け操作・DTO・イベント
    session/                      # 共通の端末側状態・タイマー
    measurement/                  # 共通インターフェースとOS別実装
    evaluation/                   # 共通の分類・判定
    sync/ / apiclient/ / localstore/
    tray/                         # 方式決定後にOS別実装を配置
  frontend/
    src/
      App.tsx                     # OS選択と共通状態の組み立て
      pages/                      # 共通の画面内容
      components/                 # 共通の表示部品
      styles/                     # 共通の色・余白など
      state/                      # OSに依存しない表示状態・操作窓口
      bridge/                     # 共通の接続契約とWails／デモの実装
      fixtures/                   # 両OSで共有するデモデータ
      platforms/
        macos/                    # Macの外枠・配置・スタイル
        windows/                  # Windowsの外枠・配置・スタイル
    wailsjs/                      # 自動生成．手編集しない
    package.json / package-lock.json
  build/                          # 共通設定とOS別の配布資材
```

OS別の画面は共通の`pages`・`components`・`state`を使用する．共通画面・状態管理から`platforms/macos`や`platforms/windows`をimportしない．OS別の外枠を選ぶ処理は`App.tsx`に集約し，各画面へOS判定を散らさない．OS固有の装飾・部品が必要なら，外枠からプロパティや表示領域として渡す．

実行OSはGoから受け取った値をbridgeで画面向けの`macos`／`windows`へ変換する．ユーザーエージェントによる推測は使わない．ブラウザでの開発時だけ明示的に表示対象OSを選択できるようにし，デモ表示であることを示す．未知のOSや未対応機能は対応不能として案内する．

OS固有のGoコードは`*_darwin.go`・`*_windows.go`またはビルドタグで分離する．共通コードから特定OSのネイティブ依存を無条件にimportしない．`main.go`や`App.tsx`を各担当が同時に変更する構成を避け，分岐先のファイルを各担当が編集する．

## 4. 共通基盤で先に揃える契約

### 4.1 表示用の型と操作

最初にGoの画面向けDTOとbridgeの契約を揃える．具体的な型定義は実装ファイルを正本とし，この文書に同じ型のコピーを置かない．Wails生成型はbridgeで吸収し，画面にprotobuf型・生成コードの配置を露出させない．

| 契約 | 最低限含める内容 |
| --- | --- |
| 起動状態 | 実行OS，利用可能なOS機能，デモ／実接続の区別，未終了セッション，権限，同期状態 |
| セッション表示 | セッションID・状態，タスク，ローカル経過秒数，最小時間，操作可否と不可理由 |
| 報酬・制限 | サーバー確定値とその有無，取得時点，制限の希望状態と適用確認状態 |
| 結果・履歴 | 作業・脱線・保留・一時停止の時間，判定根拠，報酬の獲得・利用・破棄，同期状態 |
| 設定 | タスク，分類，権限，アカウント・端末情報．未実装項目の可否も含める |
| 操作結果・失敗 | 更新後の状態，失敗分類，表示用メッセージ，再試行可否．失敗時に成功表示へ進めない |

操作名・イベント名の出発点は[フロントエンド構成の4.3節](6.フロントエンド構成.md#43-画面と状態)とする．基盤の引き渡し時には，引数・戻り値・イベントのペイロード・失敗時の挙動を実装上で確定し，両OSが同じ契約を使う．タスクの作成・選択・設定保存など，画面に必要な操作も共通の窓口へまとめる．クラウドAPI未実装を理由に独自のRPCを確定しない．

時間の受け渡しは秒単位とし，表示整形を共通化する．未取得の残高を0と扱わず，権限不明を許可済みと扱わない．終了可否はGo側が返し，画面側のタイマーから独自に確定しない．デモでも同じ境界を保つ．

### 4.2 状態とイベント

- 画面の状態保持とイベント購読は共通の`state`・`bridge`で一度だけ組み立てる．Mac／Windowsの外枠に別々のセッション管理を作らない．
- 初期状態の取得とイベント到着の競合，古い応答による上書きを防ぐ方法を共通基盤で決める．セッションIDと更新順序を照合し，OS別画面に対処を委ねない．
- 購読を解除できる窓口を用意し，画面切替・再マウントで購読やタイマーが増えないようにする．
- 操作中の連打を共通で抑止する．再送の操作IDはGo側が管理する．画面のクリック抑止だけで重複排除を保証したと扱わない．
- 一時停止直後の計測停止，サーバーのPAUSED確定，報酬評価完了，iPhone適用確認を区別する．通信断・評価失敗時に休憩可能と表示しない．
- オフライン終了・中止は同期待ちとして表示し，端末内での終了を制限解除済みと扱わない．

### 4.3 デモと実接続

同じbridge契約に対してデモ実装とWails接続実装を切り替えられる構成にする．実接続時のエラーを黙ってデモへ切り替えない．ブラウザプレビューではデモを使い，Wailsバインディングの存在を前提にしない．

デモデータは共通の`fixtures`で管理し，画面やOS別ファイルへ残高・履歴を直書きしない．最低限，開始前，作業中，停止処理待ち，停止・評価完了，完了結果，同期待ち，権限拒否，API失敗を再現する．デモの報酬は固定された表示確認用データとし，未決の報酬計算式を実装しない．

## 5. モックアップの扱い

[docs/UI](../UI/)のMac用01〜07を，画面内容と初期デザインの参考にする．Windowsも同じ情報と操作を備え，OSの慣習に合わせて外枠・配置を調整する．

| モック | 共通の画面内容 | OS別に調整する部分 |
| --- | --- | --- |
| 07 起動時 | タスク選択，開始，未終了セッションへの案内 | 初期ウィンドウの配置・サイズ |
| 04〜06 常駐操作 | 開始前・作業中・一時停止中の状態と操作 | メニューバー／タスクトレイへの導線，操作パネルの表示位置 |
| 01 フィードバック | 時間内訳，根拠，報酬の獲得・利用・破棄，同期状態 | ナビゲーションと余白 |
| 02 記録 | 期間選択，集計，セッション一覧，詳細遷移 | ナビゲーションと一覧の配置 |
| 03 設定 | タスク・分類・権限・アカウント・端末 | 権限設定への案内，OS固有機能の可否 |

モックと業務仕様が異なる場合は業務仕様を優先する．特に，モックの固定残高，終了時の追加付与や残高持ち越しを示す表現，仮の換算率，権限・制限が成功済みに見える表現をそのまま実装しない．未接続のアプリ起動・通知・制限操作を実行済みと表示しない．

Wails v2での常駐方式は未決である．共通基盤では通常ウィンドウ内で04〜06相当の操作を確認できればよく，トレイ実装をUI並行開発の着手条件にしない．メニューバーから開く本物のパネルが実装済みとは扱わない．方式の採用・追加依存は別途判断し，両OSで検証する．

## 6. 開発の順序と担当

### 段階1：Mac担当者が共通基盤を作る

Wails v2・React・TypeScript・Viteを初期化し，バージョンを固定する．共通の型・bridge・状態・デモデータと，OS別の外枠を選ぶ入口を作る．Windows用の入口には最低限の共通画面を表示し，Mac固有処理を必須にしない．この段階で7画面のデザイン完成，実API接続，永続同期キュー，ネイティブ計測，トレイ完成までは求めない．未実装機能は明示する．

**引き渡し条件（すべて満たしたらWindowsのUI実装を開始できる）：**

- [ ] 1つのGoモジュールとフロントエンド構成で依存バージョンが固定されている．
- [ ] 起動状態・操作・イベント・失敗の共通契約が実装されている．
- [ ] 共通デモで開始・一時停止・再開・終了・中止を確認でき，未終了セッションの表示へ戻れる．デモでの再起動復元と本番用の永続化は区別する．
- [ ] 最小時間未達，停止処理待ち，同期待ち，権限拒否，API失敗を共通シナリオで再現できる．
- [ ] ブラウザでMac／Windowsの外枠を選択でき，両方が同じ状態・操作窓口を使う．
- [ ] MacのWails実機で，Go呼び出しとGoからのイベント受信・購読解除を確認できる．
- [ ] 導入条件・実際に通った起動／確認コマンド・デモの選び方を`desktop/README.md`へ記載している．
- [ ] 共通基盤をレビュー可能な変更単位にまとめ，Windows担当が取得するコミット／PRを共有できる．

### 段階2：Windows担当者が起動を確認し，UIを並行開発する

Windows担当者は共通基盤を取得し，Windows上でWailsの起動・Go呼び出し・イベント受信を確認する．Mac担当者のブラウザプレビューやクロスビルドをWindows実機確認の代わりにしない．起動できない場合は，共通基盤の不具合とWindows固有の環境問題を切り分け，必要な基盤修正を先に共有する．

| 作業 | 主担当 | 主に編集する場所 |
| --- | --- | --- |
| 共通基盤・共通契約の維持 | Mac担当者（初期担当） | `main.go`，`App.tsx`，`internal/app`，`state`，`bridge`，依存設定 |
| MacのUI・起動設定 | Mac担当者 | `platforms/macos`，`platform_darwin.go`，Mac用配布資材 |
| WindowsのUI・起動設定 | Windows担当者 | `platforms/windows`，`platform_windows.go`，Windows用配布資材 |
| 共通画面・部品の追加 | 作業ごとに一人を決める | `pages`，`components`，`styles`，`fixtures` |
| 計測・判定の導入 | Bと接続する担当者 | 共通インターフェースとOS別計測実装 |

初期担当は将来の固定所有者を意味しない．共通画面の追加をどちらが担当するかは着手前に決め，同じファイルを同時に編集しない．API・同期・保存の本実装は，対応する契約と担当が揃った段階で共通部分へ導入する．

### 段階3：同じ条件で結合確認する

共通のデモシナリオを両OSで確認した後，実API・計測・同期を順に接続する．Macで確認済みでもWindowsを確認済みとしない．保存・再送・認証・トレイの実装完了は，画面デモの完成と別に判定する．

## 7. 競合と契約変更のルール

- 共通基盤の変更を先に取り込み，各OSの作業ブランチをその変更から分ける．アプリ雛形や依存ファイルを両担当が別々に初期化しない．
- 共通ファイルの編集担当を作業単位で一人にする．依存ファイル，Wails設定，起動の入口，DTO・イベントをOS別UIの変更へ便乗させない．
- 共通契約の変更時は，変更理由・影響する画面・両OSの追従箇所・確認結果をPRに記載する．両担当が確認し，互換性のない型変更は利用側の更新と揃えて取り込む．
- 自動生成コードは手編集しない．生成元と生成手順を共通化し，生成物の追跡方針を基盤初期化時に決める．
- 共通の操作・状態にOS固有の代替処理を追加する場合は，可否・未対応理由を共通契約で返す．正常終了の空実装で隠さない．
- 共通基盤，Mac UI，Windows UIをレビューできる変更単位に分ける．コミットの実行はリポジトリの承認ルールに従う．

## 8. 検証と残る判断

| 段階 | 確認する内容 |
| --- | --- |
| 共通基盤 | 型チェック・フロントエンドビルド，Goの状態遷移・操作可否，bridgeのデモ契約と失敗処理 |
| UI | 同じシナリオで情報・操作が一致すること，狭い操作パネルでの欠落，キーボード操作，読み込み・失敗・空状態 |
| Wails連携 | 各OSでの起動，Go呼び出し，イベント，購読解除，OS選択，未対応機能の表示 |
| 本接続後 | 操作IDの維持・再送，通信断・再起動，権限拒否，停止・復帰，サーバー確定とiPhone適用確認の区別 |
| 常駐方式採用後 | メニュー／トレイ，閉じる・隠す・終了の違い，最小化・スリープ復帰，各OSの配布 |

React内の状態保持・画面切替の具体方式は初期化時に決め，追加ライブラリは必要性がある場合だけ導入する．保存方式・認証情報保存・常駐方式・対応OSバージョン・CPU・PC通知・クラウドAPIの未決事項は，本書によって確定しない．

公式資料：[Wailsの構成](https://wails.io/docs/howdoesitwork/)，[共通・OS別ウィンドウ設定](https://wails.io/docs/reference/options/)，[ランタイムと起動時の制約](https://wails.io/docs/reference/runtime/intro/)．
