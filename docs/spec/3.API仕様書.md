# API仕様書

## 1. 位置づけ・確定範囲

[機能・非機能要件](../strategy/2.機能-非機能要件.md)，[ドメインモデル定義](4.ドメインモデル定義.md)，[バックエンド構成](1.バックエンド構成.md)に基づき，必要な外部APIと基本ループの契約を整理する．

iOSクライアントがAPI完成後に実装を進める順序，API引き渡し条件，画面との対応は[iOSクライアント開発フロー](6.iOSクライアント開発フロー.md)を参照する．

- **実装コードの現状**：このブランチでは，デスクトップからWails bridge・Goを経てConnect APIへ接続し，Supabase AuthのメールOTP，EnsureUser，PC端末登録，タスク取得・保存，セッション操作，分類済み活動区間の送信を実装している．macOSではネイティブ計測，ローカル送信待ち，メニューバー表示も実装している．iPhone未登録時は記録専用セッションを開始する．これらの記述は実アプリでのOTP・作業ログE2Eを確認済みという意味ではない．
- **確定した業務動作**：2節の小休憩モデル．
- **契約上の状態**：3〜8節のRPC名・論理フィールド・共通規則は契約案．protoソースにはpackage・field number等の具体値があるが，iOSを含むクライアント向けに確定・互換性保証された契約としての合意は未確認．Buf設定はGo／Connect／OpenAPI生成で，Swift生成方法は未決．
- **未決事項**：10節．途中付与条件やログイン方法などに依存するAPIを，実装準備完了とは扱わない．

通信はConnect RPC / HTTPSを用いる．各モジュールのConnect adapterを入口とし，横断処理は内部のworkflowを呼ぶ．workflow専用の外部サービスや，任意の報酬額を指定する付与APIは設けない．DB行・domain型を直接通信型にしない．

## 2. 基本ループの確定事項

報酬は**同じ作業セッション内の小休憩で使う時間**である．終了後の娯楽時間として蓄積・持ち越しはしない．

| 場面 | 作業・報酬・制限の動作 |
| --- | --- |
| 作業なし | 対象アプリの制限は解除．残高は0 |
| 開始 | オンラインで開始を受理．有効なiPhoneがなければ`tracking_only`で記録専用として開始し，制限操作を行わない．有効なiPhoneがあれば従来の制限初期化を行い，適用確認を待たずに計測開始可能 |
| 作業中 | 計測記録を定期送信し，未付与分をサーバーで評価・確定．新しい利用枠の確保は不可 |
| 一時停止 | 端末の計測は即停止．記録送信・評価とサーバーの一時停止確定後，制限連携があるセッションだけ小休憩を利用できる |
| 小休憩 | 制限連携があるセッションで，本人が残高内の秒数を指定して利用枠を確保．対象の実利用時間で消費し，使い切れば再制限．`tracking_only`では利用枠を確保できない |
| 再開 | オンラインで受理．制限連携がある場合は利用枠の残りを破棄して再制限．未充当残高は同じセッション内で保持 |
| 通常終了・中止 | 追加付与なし．未使用残高を破棄し，制限連携がある場合は残り利用枠を破棄してスマホの制限解除を要求 |

予定時間は自動終了条件にしない．通常終了は，開始時に固定した最小時間を満たした場合だけ可能とする．

現行バックエンドコードでは，新規セッションに仮の報酬Policy v2を適用する．換算式・付与条件は後述のとおりで，商品仕様として確定した値ではない．開始時にPolicy v1を保持している進行中セッションは，従来の換算を継続する．クライアントは分類結果から確定報酬を独自計算しない．

未終了セッションは本人につき1件（一時停止を含む），有効な制限対象iPhoneは1台，同時に有効な利用枠は1件とする．通常終了は本人操作かつ一時停止を除く計測時間が開始時の最小時間以上の場合のみ．中止は最小時間未満でも可能で，過去の使用済み報酬は取り消さない．

開始・再開以外の通信断中の記録は端末に保存する．終了・中止はサーバー同期後に制限解除を進める．サーバーの受理・希望する制限状態と，iPhoneの実際の適用確認を区別する．PCがオンラインでもiPhoneがオフラインなら適用は遅れ得る．

画面モックの[Mac作業後フィードバック](../UI/01_Mac_作業後フィードバック.html)には，終了後も残高を利用できるように読める箇所が残る．iPhoneの[作業中ホーム](../UI/08_iPhone_作業中ホーム.html)と[制限画面](<../UI/09_iPhone_制限画面(Shield).html>)は本節の確定事項に合わせて更新済みである．報酬は同一セッション内の小休憩だけに利用し，通常終了・中止時に未使用残高を破棄する．

## 3. 共通契約案

### 本人・端末・型

- ヘルスチェック以外はSupabase Authのユーザー用Access Tokenを`Authorization: Bearer <access_token>`で受け取り，署名・issuer・audience・期限・subjectを検証する．デスクトップのログイン方法はメールOTPとし，初回OTPではSupabase Authユーザーを作成する．業務ユーザー・PC端末の登録はログイン後にConnect APIで行う．詳細は[認証構成](6.認証構成.md)を参照する．
- 初回業務ユーザー登録は`EnsureUser`の契約案とし，検証済み主体から作成／取得する．`GetMe`は参照専用とする．Refresh Tokenは業務APIへ送らない．
- 本人のIDは認証主体から求める．クライアントが送るユーザーIDで操作対象の所有者を切り替えない．リソース・端末の所有者と失効状態を検証する．
- PCのセッション変更・計測送信は，そのセッションの計測端末に限定する案とする．PC故障時の引き継ぎ・iPhoneからの強制終了は未決．
- IDは不透明な文字列，残高・利用枠は整数秒，イベント時刻はUTCとして表現する案．区間計測の精度・丸め方は未定であり，秒未満を勝手に切り捨てない．
- 時刻は端末での発生時刻とサーバー受信時刻を区別する．競合・順序の判定を端末時刻だけに依存させない．
- 一覧はページサイズと不透明なページトークンを受け取り，次ページトークンを返す案．上限値・並び順は各一覧の実装前に確定する．

### 再送・競合・結果照会

- 変更要求には`operation_id`を付け，同一主体・操作種別・IDで重複排除する．成功済みの同一内容の再送は保存した結果を返し，異なる内容は拒否する．確定済み再送は古いバージョンでも再実行しない．
- 記録不足・一時的な評価失敗は再試行可能な未完了状態として扱い，固定された成功結果と区別する．不足分の到着後，同じ内容・操作IDで再試行できる．入力内容を修正する場合は新しい操作IDを使う．
- 状態変更・設定更新は`expected_version`で競合を検知する．計測バッチは独立したバッチID・連番で重複排除し，記録送信だけで状態変更用バージョンを無効にしない設計とする．
- 成功応答はDBコミット後に返す．応答喪失時は同じ操作IDで再送または結果照会する．結果不明を失敗と推測して新規操作を作らない．
- 操作照会では未記録・処理中・成功・失敗を区別する．未記録は「操作が実行されなかった」保証ではない．操作記録の保存期間は未定．
- セッション変更と利用枠確保，途中付与と終了は本人単位で競合制御する．終了後に付与・返還の遅延処理で残高を復活させない．

### 論理応答型

| 型 | 主な内容 |
| --- | --- |
| Session | ID，計測端末，開始時タスク設定，状態・バージョン，計測時間内訳，記録受理状況，最小時間条件，終了理由，制限連携の有無を示す`tracking_only` |
| RewardBalance | 対象セッションID（作業なしは未設定），確定済み残高秒数，残高バージョン，評価済み記録の範囲 |
| ActivityReceipt | バッチID，受理済み連続範囲，不足範囲，履歴保存／報酬評価の結果，追加確定秒数，残高 |
| UsageGrant | セッション・端末・許可ID，確保秒数，状態，確認済み消費・破棄秒数（不明は未設定），終了理由 |
| RestrictionState | セッション，制御リビジョン，希望状態（制限／時間付き解除／作業終了による解除），現在の許可，端末報告・適用済みリビジョン・報告時刻・権限状態 |
| OperationResult | 操作ID，状態，対象リソース，確定した結果または失敗理由，再試行可否 |

残高に利用枠の残り時間を含めない．破棄済み・利用済み・未確認を0という同じ値にまとめない．制御リビジョンを端末に適用・報告させ，古い解除報告で新しい制限状態を上書きしない．

### 失敗の分類

未認証，権限不足／他人の対象，対象不存在，入力不正，状態不一致，バージョン競合，同一操作IDの内容不一致，記録不足，残高不足，基盤障害を区別する．具体的なConnectコード・エラー詳細型は別途確定する．基盤障害・結果不明は同じIDで再試行し，状態競合は最新状態を取得して利用者の意図を再確認する．DB・内部実装・秘密情報はエラーに露出させない．

以下の入力には，変更API共通の操作ID・必要なバージョンも含む．参照APIは副作用を持たず，変更APIの失敗時は部分更新を残さない．

| RegisterDevice | PC・iPhone／identity | 端末登録識別子，OS，表示名 → 端末ID・状態 | 同じ登録の再送で端末を増やさない．2台目の有効iPhoneは拒否する案 |

ログイン・認証情報の発行・更新はSupabase AuthのAPIを利用し，独自のLogin／Refresh RPCは設けない．アカウント削除・端末交換の詳細は未定．端末IDの申告だけを本人認証の代わりにしない．

## 5. Focus・Reward API

### セッションと記録

| RPC案 | 呼び出し元／担当 | 入力 → 出力 | 事前条件・状態変更・主な失敗 |
| --- | --- | --- | --- |
| StartSession | PC／focus → workflow | タスクID・バージョン，計測端末ID → Session（`tracking_only`を含む），同じセッションの残高，制限連携がある場合のみRestrictionState | オンライン，本人のタスク・端末，未終了セッションなし．有効な対象iPhoneがなければ記録専用で開始し，ある場合は既存の制限初期化を行う（ポリシー無効時は失敗） |
| UploadActivityBatch | PC／focus → workflow | セッションID，バッチID・連番，計測区間・分類・根拠・判定版，collector_healthy → ActivityReceipt，RewardBalance | 対象端末のみ．区間重複・状態との矛盾・同じバッチIDの内容違いを拒否．連続して受理した範囲をサーバーで報酬評価し，受理状況・付与秒数・残高を返す |

| AbortSession | PC／focus → workflow | セッションID，バージョン，中止時刻，最終連番，未送信の残り記録 → Session，破棄結果，制限連携がある場合のみRestrictionState | RUNNING／PAUSED．最小時間条件なし．未送信の残り記録は履歴のみで報酬対象にしない．全未使用報酬を破棄し，制限連携がある場合は解除を要求 |

| GetSession | PC・iPhone／focus | セッションID → Session，評価・報酬付与／利用／破棄の要約（status，policy_version，reason，grant_stoppedを含む） | 本人のみ．報酬statusは進行中のPENDING，終了後のGRANTED／INELIGIBLEを返す．QUEUEDはPCのローカル送信待ち状態であり，APIの確定statusではない |
| ListSessions | iPhone／focus | ページサイズ・不透明なページトークン → 終了・中止済みSessionと報酬要約 | 本人の記録のみ．開始日時・IDの降順．既定20件，最大100件 |
| GetSessionOperation | PC／focus | 操作種別・操作ID → OperationResult | 本人のセッション関連操作のみ．応答喪失からの復旧用 |
| GetBalance | PC・iPhone／reward | なし → RewardBalance | 本人のみ．未終了セッションがある場合にだけ取得し，応答のsession_idを現在のsession_idと照合する．残高はセッション単位で，作業なしでは取得・表示しない |
| ListTransactions | iPhone／reward | ページサイズ・不透明なページトークン → EARN／SPEND／DISCARD等の報酬取引 | 本人の台帳のみ．発生日時・IDの降順．既定20件，最大100件．各取引の符号付き秒数と取引後残高を返す |

`ListSessions`と`ListTransactions`は既存記録を参照する読み取りAPIで，期間フィルターは設けない．各ページは安定した複合カーソルで取得し，履歴を古い順へ重複表示しない．セッション一覧には開始時刻，状態，作業時間内訳，報酬の獲得・利用・破棄要約を含める．報酬台帳は取引を個別表示し，返還条件が未確定のため，台帳に記録された取引だけを示す．

報酬付与と残高更新は同一サーバーAPIトランザクションで同期確定する．通信障害時のQUEUED表示はデスクトップのローカルoutboxに限り，サーバー未確定額を獲得額として表示しない．

### 途中付与と終了用記録の区別

バッチはセッション内の連番で並べ，各区間はセッション・計測端末と対応づける．順序逆転の受信は不足として管理し，連続して検証できた範囲を報酬評価へ進める契約案とする．一時停止時刻以降の区間をその停止前の作業として加算しない．再開後の記録は再開操作と対応づける．

新規セッションに適用する仮ポリシー v2 は，`reward_seconds = 60 × floor((T + R) / 300秒)` とする．D・U・I・一時停止時間は報酬換算時間に含めない．付与ごとに `Q = (T + R + D + I) / E >= 0.70`，`K = T + R + D >= 300秒`，計測コレクターが正常であることを確認する．条件を満たさない間は付与を保留する．一度でも報酬を付与した後に条件を外れた場合，そのセッションの追加付与を停止するが，既付与・利用済み報酬は取り消さない．通常終了・中止時は追加付与せず，未使用残高を破棄する．

定期送信と一時停止直前の送信は，未終了セッションについて途中付与の評価契機となる．バッチ分割・再送で報酬が増えないよう，累積 T+R の5分ブロックとの差分を付与する．進行中セッションは開始時のポリシーバージョンを固定し，既存 v1 セッションは従来の 3秒あたり1秒換算を継続する．v2 の換算率・条件はPoCから得た仮値であり，上限・ボーナス等を含む商品仕様は未確定とする．

端末が終了・中止を選択した後の残り記録は，通常の付与対象バッチとして先に送らず，終了・中止要求に含めて履歴用に保存する．終了要求の最大サイズと，それを超える場合の履歴専用分割アップロード方式は実装前の未決事項とする．

終了・中止後の遅延バッチは，内容が整合する欠落分のみ履歴用として受理し，付与対象外であることを応答する．確定済み評価を黙って変更せず，追加履歴と確定評価を区別する．終了と途中付与が競合した場合，先に付与がコミットすれば終了処理で残高を破棄し，終了が先なら追加付与しない．

## 6. Restriction API

Apple固有の選択トークンは端末に保持する．APIは制限モード・設定版・権限状態などのメタデータを扱う．

クライアントは`TARGET_MODE_SELECTED_APPS`のみを送信する．`TARGET_MODE_DEVICE_WIDE`は既存契約との互換性のためproto enumに残すが，モバイルUIからは選択できない．`allowed_apps_policy`は`NONE`とし，Appleの選択tokenは端末内に保持してAPIへ送信しない．

| RPC案 | 呼び出し元／担当 | 入力 → 出力 | 事前条件・状態変更・主な失敗 |
| --- | --- | --- | --- |
| UpdateRestrictionPolicy | iPhone／restriction | 端末ID，設定版，対象モード，端末側設定の版・設定済み状態 → 設定 | 本人の有効なiPhoneのみ．旧端末からの再登録後，新端末へ制御状態を引き継ぎ，適用・権限報告を再要求する．有効な利用枠がある間は拒否 |
| GetRestrictionPolicy | PC・iPhone／restriction | 端末ID → 設定メタデータ | 本人のみ．PCへAppleトークンを公開しない |
| ReserveUsageGrant | iPhone／restriction → workflow | セッションID・期待バージョン，端末ID，要求秒数 → UsageGrant，残高，RestrictionState | PAUSEDかつ停止直前まで評価済み，有効利用枠なし，正の秒数・残高内．確保と発行を原子的に処理．作業中／終了後は拒否 |
| GetUsageGrant | PC・iPhone／restriction | 許可ID → UsageGrant | 本人のみ．終了済み許可も結果照会可能 |
| GetRestrictionState | PC・iPhone／restriction | 端末ID → RestrictionState | 本人のみ．現在の許可と希望状態・最終報告をまとめて取得 |
| ReportRestrictionState | iPhone／restriction | 端末ID，制御リビジョン，許可ID（必要時），適用状態・時刻，権限状態，失敗情報 → 受理結果・最新RestrictionState | 対象端末のみ．古い報告を最新の適用確認にしない．解除成功報告だけで失効済み許可を復活させない |
| ReportUsage | iPhone／restriction | 許可ID，報告連番，累積実利用秒数，観測時刻 → UsageGrant，最新RestrictionState | 対象端末のみ．差分加算ではなく累積値の再送を重複排除する案．減少・確保量超過は整合性エラーとして扱い精度問題を記録 |
| GetRestrictionOperation | iPhone／restriction | 操作種別・操作ID → OperationResult | 本人の利用枠確保・設定・報告操作の照会 |

利用枠消費完了時には，セッションが継続中なら端末で再制限する．終了後の遅延した消費完了イベントで再制限しないよう，端末は最新の制御リビジョンを優先する．作業終了による解除は利用枠を必要とせず，消費カウントを継続しない．

解除失敗・権限取消・消費報告不足は成功扱いしない．返還条件は未定であり，自動返還RPCは確定しない．作業終了後に失敗報告が届いても残高を復活させない．制限解除と計測の精度，端末が長時間オフラインの場合の収束はPoC対象とする．

## 7. 横断処理と再同期

| 操作 | 同一トランザクションで確定する範囲 |
| --- | --- |
| 開始・再開 | focusの作業状態，restrictionの利用枠失効・希望状態／リビジョン，操作結果．新規開始通知を導入する場合はOutboxも含む |
| 記録受理・途中付与 | focusの記録・評価範囲，rewardの付与対象識別・付与記録・残高・履歴，操作結果，通知導入時のOutbox／抑制状態 |
| 一時停止 | 必要範囲の受理・評価済み確認とPAUSEDへの遷移，操作結果 |
| 利用枠確保 | PAUSED・利用可能条件の確認，rewardの減算・履歴，restrictionの許可と希望状態，操作結果 |
| 終了・中止 | focusの終了状態と履歴用記録，rewardの未使用残高破棄と履歴，restrictionの利用枠失効・解除希望状態，操作結果 |

通知送信・端末の制限操作をDBトランザクションに含めない．通知失敗は業務確定の取消理由にしない．

再接続時は，変更要求の同じIDによる再送または操作照会の後に，`GetCurrentSession`／`GetSession`，`GetBalance`，`GetRestrictionState`で最新状態を取得する．複数の参照APIを単一時点のスナップショットと仮定せず，セッションID・各版を照合し，食い違う場合は再取得する．端末の「終了同期待ち」とサーバーのRUNNINGが一時的に併存することを表示する．

通知送信は内部処理とし，任意の相手へ通知を送る汎用APIは公開しない．既存の作業中・一時停止中の報酬通知抑制は維持する．途中報酬と小休憩の状態は応答・画面で確認でき，通知がなくても基本ループを成立させる．

`CreateGroup`は認証ユーザーの業務User ID、UUID形式の`operation_id`、1〜100文字のグループ名を受け取る。前後の空白を除去し、グループと作成者のACTIVE membershipを同一トランザクションで作成する。同じユーザー・operation ID・同じ内容の再送は確定済み応答を返し、同じIDで異なる内容を送った場合は競合エラーとする。

`CreateInvitation`はグループのACTIVE memberなら誰でも発行できる。リンクには256-bitのランダムtokenを含め、有効期限は発行から7日、受諾は1回限りとする。DBにはtoken hashを保存し、API応答の再送に必要なtokenだけをoperation responseとして保持する。`AcceptInvitation`は認証済みユーザーをACTIVE memberにし、再送時は同じoperation IDで確定応答を返す。退出済みユーザーは新しい有効招待から再参加できる。`LeaveGroup`は本人のmembershipだけをLEFTにし、ACTIVE memberが0人ならgroup・membership・招待を同一トランザクションで削除する。

`UpdateDisplayName`は本人の公開表示名を前後空白除去後に1〜30文字で保存する。初期値は「メンバー」とし、グループのメンバー応答に表示名を含める。表示名は本人が設定し、所属するACTIVEグループのメンバーだけに共有する。`UpdateAvatar`は許可された固定カタログの`avatar_id`を本人のUserへ保存し、同じメンバー応答で共有する。画像ファイルはクライアント同梱とし、DBに画像データや外部URLを保存しない。

プロフィール画像の許可IDは`dragon`、`puppy`、`cat`、`hedgehog`、`rabbit`、`chick`、`bird`、`penguin_blue`、`penguin_pink`、`slime`。新規Userの既定値は`chick`。

`GET /v1/group/work-starts`はBearer認証を要求し、必須の`after_started_at`と任意の`after_event_id`を複合カーソルとして受け取り、時刻・event IDの昇順で次ページを返す。`page_size`は省略時50、最大100。次回は応答の`next_started_at`と`next_event_id`をそのまま渡す。イベントは新規セッション開始時に、開始者がACTIVEグループメンバーなら作業セッション作成と同じDBトランザクションで1件記録する。再開は記録しない。応答は開始時刻と不透明なevent IDのみで、タスク名・カテゴリを含めない。開始者本人を除外し、開始時に同じグループへ参加していた呼び出しユーザーだけへ返す。クライアントは初回のカーソルを現在時刻にして過去イベントを通知しないようにし、その後30秒ごとに取得してカーソルを永続化する。

`RegisterNotificationEndpoint`は認証済み利用者の有効なiOS端末を安定した`registration_id`で特定し、APNs tokenと`DEVELOPMENT`／`PRODUCTION`環境を端末単位で登録・更新する。認証session IDが更新されても端末を特定できる。`DeleteNotificationEndpoint`も本人の`registration_id`を指定して端末の登録を削除する。グループ作業開始時には同一DBトランザクションで各メンバーの登録済みiPhone向けOutboxを作成する。送信直前にもグループ所属を再確認し、作業開始の事実だけを通知する。タスク名などの作業内容は送らない。APNs設定がない環境ではOutboxを保留する。ローカルAPIは30秒間隔のプロセス内workerで再試行するが、Cloud Runでの永続実行を保証しないため、本番の確実な再試行にはCloud Scheduler／Tasks等の実行基盤が別途必要。APNsの外部送信とDB更新の境界では重複配信の可能性がある。

## 9. 受け入れ・競合シナリオ

1. 未認証・改ざんJWT・期限切れ・別issuer／audience・他人のリソース・失効端末を拒否する．初回同時登録で業務Userを増やさず，鍵更新後も正しく検証する．同時開始は1件だけ成功し，一時停止中も新規開始を拒否する．
2. 同じ記録の再送・別バッチへの重複混入・順序逆転で二重付与しない．不足範囲を返し，記録受理と付与済み範囲を区別する．
3. 一時停止直前の記録不足・評価失敗では利用枠を確保できない．必要記録が揃えば同じ停止操作を再試行できる．
4. RUNNING／終了済みでの利用要求，残高不足，重複する利用枠要求を拒否する．同じ操作の再送は既存許可を返す．
5. 未充当残高20分，利用枠10分のうち3分使用後に再開すると，枠の残り7分だけを破棄し残高20分を保持する．終了・中止ならその20分も破棄する．
6. 最小時間未満の通常終了は拒否し，中止は可能．どちらの終了処理も追加付与せず，残高0・利用枠失効・制限解除要求を確定する．
7. 終了と途中付与・利用枠確保の並行要求，終了後の遅延記録・失敗報告で残高や許可が復活しない．通常終了と中止は二重確定しない．
8. 各横断処理の途中失敗で部分更新が残らない．応答喪失後も同一IDの再送・照会で結果を確認できる．
9. PCのオフライン終了は同期待ちになる．同期後もiPhone未確認なら解除済みと表示しない．古い報告・古い制御指示で最新状態を戻さない．
10. 通知不達でも残高・状態を参照できる．途中付与が起きても抑制済み通知を終了後に再送しない．
