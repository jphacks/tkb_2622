# インフラ構成

## 1. 採用方針と現在の状態

認証はSupabase Auth，業務DBはSupabase PostgreSQLを採用する．APIはCloud Run上のGo / Connect RPCとして維持する．**コード・ローカルCompose・マイグレーションはPostgreSQL向けに移行済み**であり，ローカルではPostgreSQLコンテナで起動できる．**Supabaseプロジェクトの作成，クラウド上の接続・権限設定，Cloud Runへのデプロイは未実施**．本書はクラウド上の目標構成を定め，実装済みの範囲は[バックエンドのREADME](../../backend/README.md)に記載する．

| 要素 | 責務 |
| --- | --- |
| Cloudflare | Workersによる業務APIの入口（`workers.dev`）とCloud Runへの転送 |
| Cloud Run | JWT検証，業務認可，モジュール・workflowの実行 |
| Supabase Auth | ログイン・セッション・トークン更新 |
| Supabase PostgreSQL | 業務ユーザー，作業記録，残高・取引，制限・グループ・通知の永続化 |
| APNs | iPhone通知．制限操作そのものは端末が実施 |

CloudflareとGoogle CloudのリソースはTerraformで管理する．CloudflareからCloud Runへは，Cloudflare Workersが受けたリクエストをCloud RunのURLへ転送する．費用をかけないためドメインは取得せず，Workerを`workers.dev`のURLで公開する．自分のゾーンを持たないため，ゾーン単位のWAF・レート制限・SSL/TLS設定は使わない．GCPプロジェクトはdev／prodで共用し，リソース名で環境を分ける．ディレクトリ構成・管理範囲・state・適用順序は[infraのREADME](../../infra/README.md)を参照する．

クライアントはAuthに直接ログインし，業務要求はGo APIへ送る．Supabase Authの採用自体は業務DB変更の必須条件ではないが，本プロジェクトでは運用先をまとめるためPostgreSQLも採用する．モジュールごとのデータ所有と共通DBトランザクションは維持する．

## 2. DBへのアクセスと公開範囲

業務SQLはGo APIのpersistenceから実行する．Supabase Data API経由でクライアントが残高等を更新する経路は設けない．業務テーブルは非公開の`app`スキーマに置く設計とし，Data APIの公開スキーマに含めず，`anon`／`authenticated`へアクセス権を付与しない．Data APIを利用しない初期構成では無効化する方針とする．公開制御はスキーマ・権限を含めて検証する．[Data APIの保護](https://supabase.com/docs/guides/api/securing-your-api)

Go API用DBロールは業務テーブルへの必要な権限だけを持ち，DDL用のマイグレーションロールを分離する．GoのSQL接続にユーザーJWTの認可情報が自動反映されるとは扱わない．本人・所有者・所属の認可はapplicationで必須とする．RLSを追加する場合はDBロールとトランザクション内の主体設定を別途設計し，単にRLSを有効化しただけで認可済みとしない．

Supabase管理の`auth`スキーマはgooseの管理対象にしない．業務スキーマの正本は既存方針どおりgoose SQLとし，同じDDLをSupabase CLIのマイグレーションと二重管理しない．

## 3. 接続・設定の方針

Supabaseは直接接続，セッションプーラー，トランザクションプーラーを提供する．接続先はDashboardから取得し，ネットワーク到達性・接続数・ドライバー設定に応じて選ぶ．マイグレーションは直接接続を基本とし，IPv4環境ではセッションプーラーの利用可否を検証する．[PostgreSQL接続方法](https://supabase.com/docs/guides/database/connecting-to-postgres)

Cloud Runのアプリ接続は共有トランザクションプーラーを第一候補とする．採用時はprepared statement等のセッション状態依存を無効化・排除し，共通トランザクションの動作を検証する．インスタンスごとの接続数とCloud Run最大インスタンス数からDB接続予算を設定する．実測に応じて直接接続／セッションモードも比較し，接続方式を確定する．[プーリングと制約](https://supabase.com/docs/guides/database/connecting-to-postgres#transaction-mode-limitations)

現行コードはprepared statementを使わない設定（pgxの`QueryExecModeExec`）でPostgreSQLに接続しており，トランザクションプーラーと両立する．プーラー経由の動作はSupabase上で未検証．

| 設定 | 利用側 | 用途 | 状態 |
| --- | --- | --- | --- |
| DATABASE_URL | API | API用PostgreSQL接続．実行用ロール，TLS（`sslmode=require`以上）を設定 | 実装済み |
| DB_MAX_CONNECTIONS | API | インスタンスあたりの最大接続数．既定5，1〜100 | 実装済み |
| MIGRATION_DATABASE_URL | migrate | DDL適用専用接続．通常のAPIに不要な権限を分離 | 実装済み |
| SUPABASE_JWT_ISSUER / SUPABASE_JWT_AUDIENCE | API | 許可するissuer・audience．JWKSの取得先もissuerから固定 | 実装済み |
| SUPABASE_URL | クライアント | 環境ごとのAuthプロジェクトURL | クライアント未実装 |
| SUPABASE_PUBLISHABLE_KEY | クライアント | クライアントがAuthを呼ぶための公開可能なキー．本人のアクセストークンとは別 | クライアント未実装 |

DB認証情報・SMTP認証情報・外部プロバイダーの秘密は端末へ配布しない．DB接続情報はサーバー側の秘密管理で渡す．通常のJWT検証・SQLアクセスのためにSupabaseのsecret／service_roleキーをクライアントへ持たせない．クラウドのDB接続はTLS必須とし，接続文字列・トークンをログへ出力しない．

ローカルのDBはPostgreSQLコンテナ（`backend/compose.local.yaml`）を使い，`backend/dev/postgres/001_roles.sql`でAPI実行用ロール`tkb_app`を作成する．このロール定義・パスワードはローカル専用であり，Supabaseでは実行用ロールを別途作成する．Auth結合確認はSupabase CLIのローカル環境または開発専用プロジェクトを使う案とする．

## 4. Supabaseへの接続の残作業と完了条件

PostgreSQLドライバー・接続処理，ローカルCompose，環境変数，gooseの方言・スキーマ，sqlc，Supabase AuthのJWT検証はコード上で移行済み．旧SQLite用のローカルボリューム`tkb-backend-local_sqlite-data`は自動削除しない．旧DB（SQLite／Turso）からのデータ移送は行わない前提とする．

1. 環境ごとのSupabaseプロジェクトを作成し，リージョン・料金プランを決める．
2. Supabase上にAPI実行用ロールを作成し，`app`スキーマへの必要な権限だけを付与する．マイグレーション用の接続とは分ける．
3. `MIGRATION_DATABASE_URL`で`migrate up`を実行し，`app`スキーマ・一意制約が作成されることを確認する．
4. `DATABASE_URL`・`SUPABASE_JWT_ISSUER`をCloud Runに設定し，プーラー経由の接続，共通トランザクション・ロールバック，同時要求を検証する．業務テーブルにクライアント（Data API）から直接アクセスできないことも確認する．
5. Supabase Authで発行したトークンで初回業務User登録を両クライアントから確認する．
6. README・デプロイ手順を検証結果に合わせて更新する．

プロジェクト・リージョン・料金プラン，接続数とインスタンス上限，バックアップ・復元，監視，失効反映，SMTP，`run.app` URLへの直接アクセス（Cloudflareの迂回）の防止は未決．本書の更新では外部リソースの作成・課金・デプロイを行わない．
