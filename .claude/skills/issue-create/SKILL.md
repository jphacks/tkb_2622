# 要望を Issue にする

1. 目的と対象を整理する。既存資料から判断できない重要な点だけを確認する。
2. `INDEX.md` と関連資料を確認する。必要なら `docs-navigator` を使う。仕様が空・未記載なら未決事項に記載し、架空の仕様リンクや確定済みの契約を作らない。
3. 対象を `backend`・`desktop`・`mobile`・`infra`・`poc`・ドキュメント・開発設定から選び、やることと対象外を明確にする。独立して検証できる単位に分ける。
4. `.github/ISSUE_TEMPLATE/feature.md` の本文項目を使い、目的・仕様参照・範囲・完了条件・未決事項を埋める。不具合では再現手順、期待結果、実際の結果も記載する。
5. 完了条件には、観察できる受け入れ基準、検証方法、必要なドキュメント更新を含める。テスト基盤が未導入ならその事実と適切な検証方法を記載し、特定のテストツールを既存扱いしない。
6. GitHub への作成が依頼されている場合は、現在のリポジトリで `gh repo view --json nameWithOwner --jq .nameWithOwner` を実行し、対象を取得する。取得できなければ `git remote -v` を確認し、対象を確定できない場合は本文を提示して不足情報を確認する。
7. 本文は一時ファイルに保存し、`gh issue create --repo <取得した対象> --title <タイトル> --body-file <本文ファイル>` で作成する。ラベルは必要な場合だけ一覧で存在を確認して指定する。草案のみの依頼では投稿しない。

作成後は Issue の URL と完了条件を報告する。投稿に失敗した場合は草案と原因を報告し、作成済みと扱わない。
